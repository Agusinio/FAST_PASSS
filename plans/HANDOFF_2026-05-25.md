### Modelo de ejecución: Independiente (no acumulativo)

Cada botón ejecuta **SOLO su fase**. No hay dependencia entre ellas:
- **F1** coloca SOLO items con `horaEntradaOnAir` real.
- **F2** coloca SOLO items con OnAir deducido (salta los que ya tienen OnAir real).
- **F3** coloca SOLO items con `horaEntradaPrevista` (salta los que tienen OnAir real o deducido).

**Sin `Markers.clear()`**: Los marcadores de otras fases se preservan intactos. Cada fase usa [`placeByPrefixes()`](jsx/modules/8_Markers.jsx:172) que hace upsert: si el marcador ya existe (mismo prefijo en el comentario), lo mueve; si no, lo crea.

### Formato de comentario de marcador

```
"03 - Titol de la notícia"
"04i - intro col·loqui"
```

El prefijo se extrae como el texto antes de ` -` (espacio + guion). Esto permite a [`placeByPrefixes()`](jsx/modules/8_Markers.jsx:172) indexar marcadores existentes por prefijo y decidir si mover o crear.

## 🔬 FÓRMULAS DE POSICIONAMIENTO (BUG #3 FIX 2026-05-26)

### Fórmula unificada (aplica a F1, F2, F3)
```
idealPosSec = clipStart + (tcSec - worldSecMediaStart) - clipInPoint
```
Donde:
- `clipStart` = posición `start` del clip V1 real en el timeline (de `clips[0].start`)
- `clipInPoint` = In point real del clip V1 (de `clips[0].inPoint`)
- `worldSecMediaStart` = media start del cleanFeed (del manifest)
- `tcSec` = tiempo de emisión en segundos (OnAir, Deducido o Prevista)

### F1·OnAir ([`flow_assembly.js`](js/workflows/flow_assembly.js))
```
tlClipStartSec = clipStart + (refF1 - worldSecMediaStart) - clipInPoint
idealPosSec = tlClipStartSec + (itemOnAirSec - refF1)
           = clipStart + (itemOnAirSec - worldSecMediaStart) - clipInPoint  ✓
```
Donde `refF1` = cascada: OnAir → OnAirDeducido → blockInSec

### F2·OnAirDeducido / F3·Prevista
```
anchorEfTimelineSec = clipStart + (anchorEfectiva - worldSecMediaStart) - clipInPoint
idealPosSec = anchorEfTimelineSec + (tcSec - anchorEfectiva)
            = clipStart + (tcSec - worldSecMediaStart) - clipInPoint  ✓
```
Donde `anchorEfectiva` = TC del primer ítem con OnAir (real o deducido)

### Invariante
```
timeline position = clipStart + (tcEmissio - mediaStart) - clipInPoint
```
`clipStart` y `clipInPoint` se leen del timeline real en cada ejecución. `tlBlockInPointSec` del manifest solo se usa como fallback si no hay clips disponibles.

## 🧠 PARADIGMA "BRAIN vs MUSCLE" (Implementación Final)

| Capa | Responsabilidad | Ejemplo |
|------|----------------|---------|
| **JavaScript (Brain)** | Clasificación, cálculo, decisión | `hasOnAir`, `_deduceOnAirEntrada()`, `horaEntradaPrevista`, construir `placements[]` |
| **ExtendScript (Muscle)** | Operaciones atómicas sobre PPro DOM | `placeByPrefixes()`: indexar, mover, crear — todo en una llamada |

**Principio**: El JS construye el array `placements` con TODA la información necesaria (prefijo, tiempo, comentario, color). El JSX recibe ese array y ejecuta la operación atómica sin tomar ninguna decisión de negocio.

### ISSUE #1: Marcadores duplicados — D15·FASE0
**Causa**: D15 recolocaba items ya posicionados por F1/F2/F3, creando duplicados.
**Solución**: D15·FASE0 envuelto en `if(false)`. El bloque completo está preservado para F5+.

### ISSUE #2: Marcadores desplazados (ajustándose a cortes en F1)
**Causa**: La referencia `refF1` no seguía la cascada correcta OnAir→OnAirDeducido→blockInSec.
**Solución**: Implementada cascada en 3 niveles con `anchorEfectiva`.

### ISSUE #3: Bug `_deduceOnAirEntrada` — no acumulaba duración del ítem ancla
**Causa**: Al retroceder desde el ítem target, el bucle no sumaba la duración del ítem OnAir encontrado.
**Solución**: Añadida acumulación de `anchorItem.duradaSec` al TCOut.
**Archivo**: [`js/core/escaleta_reader.js`](js/core/escaleta_reader.js) — método `_deduceOnAirEntrada()`

### ISSUE #4: Duplicados en F4/APROXIMATS
**Causa**: F4a (snapToCutFaro) y F4b (APROXIMATS Greedy Bidireccional) recolocaban items ignorando posiciones ya establecidas.
**Solución**: Todo F4a+F4b+F5 desactivado con `if(false)`.

### ISSUE #5 (BUG #3): Offset ~9s en todos los marcadores (FIX 2026-05-26)
**Causa**: [`_calcTemporalAnchors()`](js/workflows/flow_assembly.js:330) usaba `tlBlockInPointSec` del manifest como valor del In point del clip MP4. Este valor se calcula en [`calcPrecisionTrimBounds()`](js/core/escaleta_reader.js) (Tier-10) en el momento de creación del proyecto y se persiste en el manifest. Si el usuario edita posteriormente el clip en Premiere (cambiando su `inPoint`), el manifest contiene un valor **stale** que no refleja el estado real del timeline.

El `Clips.get()` de JSX ya devuelve el `inPoint` y `start` reales del clip V1, pero estos valores nunca se usaban en el cálculo de áncoras.

**Síntoma**: `tlClipStartSec = (refF1 - worldSecMediaStart) - tlBlockInPointSec = (75719 - 75540) - 170 = 9s`. Este offset de 9s desplazaba TODOS los marcadores a la derecha.

**Solución**:
1. [`_calcTemporalAnchors()`](js/workflows/flow_assembly.js:330) acepta un 4º parámetro `clips` (opcional, fallback al manifest).
2. Lee `clips[0].start` y `clips[0].inPoint` directamente del timeline.
3. **Fórmula unificada**: `clipStart + (tcSec - worldSecMediaStart) - clipInPoint`
   - Para F1: `tlClipStartSec = clipStart + (refF1 - worldSecMediaStart) - clipInPoint`
   - Para F2/F3: `anchorEfTimelineSec = clipStart + (anchorEfectiva - worldSecMediaStart) - clipInPoint`
4. Log diagnóstico: `🔧 [BUG3·FIX] Clip V1 real: start=Xs, inPoint=Ys vs manifest tlBlockInPointSec=Zs`
5. Todas las llamadas a `_calcTemporalAnchors()` desde F1, F2, F3 y `_setupEstructural` pasan `clips` como 4º argumento.

**Impacto**: Cero cambios en JSX. Solo [`flow_assembly.js`](js/workflows/flow_assembly.js) modificado.

> **Estado**: D0·D1·D2 ✅ COMPLETADO | D3·D4 ⛔ PENDIENTE

### Objetivo

Convertir las posiciones "ideales" (basadas en TC de emisión) en posiciones "reales" (ancladas a cortes del timeline), usando detección de densidad de cortes y un algoritmo de snap por correlación.

### Problema detectado

Los 3 flujos actuales (F1·OnAir, F2·Deducido, F3·Prevista) colocan marcadores en su posición ideal según el TC, pero **sin ajustar a los cortes reales del timeline**. Se han observado desfases de hasta ~2s entre la posición ideal y el corte real. `DensityFootprint v2` ya calcula zonas HIGH/LOW, rupturas multi-señal y pares DP+DIR, pero **nadie consume estos datos**.

### Algoritmo CorrelationSnap (D1) — Implementado

```javascript
// Parámetros reales (ver _correlationSnap en flow_assembly.js:404-412)
BUCKET_SIZE       = 0.04   // 1 frame @ 25fps (en vez de 0.1s planificado)
SEARCH_WINDOW     = 2.0    // ±2s (en vez de ±5s planificado)
MIN_CONFIDENCE    = 0.30   // 30% mínimo
ON_AIR_WEIGHT     = 1.0
DEDUCED_WEIGHT    = 0.7
DENSITY_BONUS     = 1.5    // bonus si hay ruptura de densidad cerca del marcador
DENSITY_PROXIMITY = 0.5    // radio para considerar "cerca de ruptura"
EXCLUDE_ZERO      = 0.01   // excluir marcador en 00:00

ALGORITMO (histograma de buckets):
  1. PARA CADA marker:
     - Clasificar: OnAir (tiene horaEntradaOnAir real) vs Deducido (resto)
     - Buscar corte más cercano en ±SEARCH_WINDOW
     - Calcular bucket = round(δ / BUCKET_SIZE)
     - peso = peso_base * (cercaDeRuptura ? DENSITY_BONUS : 1.0)
     - Acumular peso en histograma[bucket]
  
  2. Bucket ganador = mayor peso acumulado
     confianza = peso_ganador / peso_total
  
  3. SI confianza ≥ 0.30:
       Δ_consenso = media de los δ dentro del bucket ganador
     SINO:
       Δ_consenso = null (no aplicar)

  4. Retorna { delta, confidence, votes, totalWeight, onAirCount, deducedCount, breakdown }
```

### Semántica de `isDefinitiu` — Implementado sin nuevo JSX

El campo `name` del marcador de Premiere actúa como flag:

- `name: "definitiu"` → definitivo (colocado por F4, no modificable por F5/F6)

### Orden de ejecución recomendado (editor)

```
F1·OnAir → F2·Deducido → F3·Prevista → F3.5·CorrelationSnap → F4·DensitySnap → F5·OrphanSnap → F6·Gràfics
```

Cada botón es independiente y no acumulativo. **F3.5** aplica Δ de consenso solo a OnAir+Deducidos no-definitivos y los marca como `definitiu`; si falla (confianza < 30%), los marcadores quedan no-definitivos y F4 los recoge. **F4 v2** aplica matching **seqüencial** (por orden, no por proximidad): el marcador N-èsimo se emparella con el break N-èsimo. Sin ventanas de tiempo. Procesa tanto Previstos como OnAir/Deducido orfes (los que F3.5 no pudo correlacionar). **F5** procesa los marcadores sobrantes no-definitivos (los que F4 no pudo emparejar por falta de breaks). **F6** coloca gráficos en gaps.

### Notas sobre F3.5·CorrelationSnap y F4·DensitySnap v2 (2026-05-26)

- **F3.5·CorrelationSnap** (`correlationSnapMarkers`): Extrae la lógica de `_correlationSnap()` que antes estaba dentro de F4. Filtra solo marcadores OnAir + Deducido (excluye Previstos). Aplica un único Δ de consenso global. Si la confianza es < 30%, retorna sin marcar nada como `definitiu` — esos marcadores pasan a F4.
