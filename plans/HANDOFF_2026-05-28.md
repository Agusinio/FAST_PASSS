#### BUG #8 — CRASH F2: `JSON.parse` de respuesta `"ERR:..."` de JSX

**Archivos modificados**: [`flow_assembly.js`](js/workflows/flow_assembly.js)

**Raíz del problema**: `callJSX()` en [`utils.js`](js/core/utils.js:22) envuelve el script en `try{...}catch(e){'ERR:'+e.message}`. Si el JSX falla, retorna `"ERR:..."` (que empieza por `E`), y `JSON.parse("ERR:...")` lanza `SyntaxError: Unexpected token E in JSON at position 0`.

**Fix**: Nuevo helper `_safePlaceByPrefixes` (líneas 62-77) que envuelve todas las llamadas con try/catch, maneja respuestas `ERR:`, strings vacíos, y JSON malformado. Retorna fallback seguro `{placed:0, moved:0, created:0}`.

**7 call sites reemplazados**: F1 (línea 782), F2 (línea 865), F3 (línea 958), F3.5 (línea 1094), F4 (línea 1272), F5 (línea 1452), F6 (línea 1571).

```javascript
// ANTES (crash si JSX falla):
var result = JSON.parse(await callJSX('Markers.placeByPrefixes(\'' + JSON.stringify(placements) + '\')'));

// AHORA (protegido):
var result = await this._safePlaceByPrefixes(placements, 'F2·Deducido');
```

#### BUG #9 — Color de marcadores perdido al hacer delete+create

**Archivos modificados**: [`8_Markers.jsx`](jsx/modules/8_Markers.jsx)

**Raíz del problema**: `_setMarkerColor()` llamaba a `markerObj.setColorByIndex()` (API de Premiere) que cambia el color visual pero **NO** escribe la propiedad `markerObj.color`. Al leer `existing.color` después, devolvía `-1`, y el nuevo marcador se creaba sin color → verde por defecto.

**Fix**: [`_setMarkerColor` línea 35](jsx/modules/8_Markers.jsx:35) ahora **siempre** asigna `markerObj.color = colorIdx` **ANTES** de llamar a `setColorByIndex()`. También se ajustó la condición en [`placeByPrefixes` línea 221](jsx/modules/8_Markers.jsx:221) de `p.colorIdx !== undefined && p.colorIdx !== null` a `p.colorIdx !== undefined && p.colorIdx !== null && p.colorIdx >= 0`.

```javascript
// ANTES:
function _setMarkerColor(markerObj, colorIdx) {
    if (colorIdx === null || isNaN(colorIdx)) return;
    colorIdx = Math.max(0, Math.min(7, colorIdx));
    if (typeof markerObj.setColorByIndex === "function") {
        markerObj.setColorByIndex(colorIdx);  // ← NO escribía .color
    } else {
        markerObj.color = colorIdx;           // ← solo en else
    }
}

// AHORA:
function _setMarkerColor(markerObj, colorIdx) {
    if (colorIdx === null || isNaN(colorIdx)) return;
    colorIdx = Math.max(0, Math.min(7, colorIdx));
    markerObj.color = colorIdx;               // ← SIEMPRE asigna
    if (typeof markerObj.setColorByIndex === "function") {
        markerObj.setColorByIndex(colorIdx);
    }
}
```

#### BUG #10 — Marcador rojo inesperado: lógica de color incorrecta

**Archivos modificados**: [`flow_assembly.js`](js/workflows/flow_assembly.js)

**Raíz del problema**: La lógica `line.agrupacio ? 6 : 1` no implementaba la especificación completa de [`MARKER_COLORS.md`](docs/specs/MARKER_COLORS.md):
- 🔵 Azul (6) → item con `agrupacio != null`
- 🟡 Amarillo (4) → sin agrupacio, `durada = 0`
- 🔴 Rojo (1) → sin agrupacio, `durada > 0`

**Fix**: Nuevo helper `_getColorIdx` (líneas 86-95) con parsing inline de durada. Aplicado en **6 puntos**: 3 estructurales (F1 línea 765, F2 línea 849, F3 línea 939) + 3 UNGROUPED (F1 línea 788, F2 línea 872, F3 línea 964).

```javascript
// ANTES:
var colorIdx = line.agrupacio ? 6 : 1;   // ← no distingue rojo/amarillo

// AHORA:
_getColorIdx: function (line) {
    if (line.agrupacio) return 6;        // 🔵 Azul
    var dStr = line.durada || line.duradaOnAir || '0:00';
    var parts = dStr.split(':').map(Number);
    var dSec = 0;
    if (parts.length === 2) dSec = parts[0] * 60 + parts[1];
    else if (parts.length === 3) dSec = parts[0] * 3600 + parts[1] * 60 + parts[2];
    else dSec = (typeof parts[0] === 'number') ? parts[0] : 0;
    return dSec === 0 ? 4 : 1;           // 🟡 Amarillo : 🔴 Rojo
},
```

#### BUG #11 — OUT del MP4 incorrecto por `duradaOnAir` inconsistente

**Archivos modificados**: [`escaleta_items.js`](js/core/escaleta_items.js), [`escaleta_bounds.js`](js/core/escaleta_bounds.js)

**Evidencia en TNC 2026-05-27 V2**:
- Item 18: `horaEntradaOnAir=14:10:49`, `duradaOnAir=0:21` → sortida calculada = 14:11:10
- Siguiente video 19FT: `horaEntradaOnAir=14:12:28` → **78s después**
- El bloque se recortó a 54s cuando debería extenderse hasta ~14:12:28

5 items más con `duradaOnAir` de 5-9 segundos en la misma escaleta, todos sospechosos.

**Principio**: `horaEntradaOnAir` del siguiente ítem es un **hecho duro** del playout. `duradaOnAir` es un **dato derivado** que puede ser incorrecto. Cuando entran en conflicto, el hecho duro gana.

**Fix en tres capas**:

1. **[`getItemSortidaSec`](js/core/escaleta_items.js:193)**: El nivel 3 (siguiente OnAir) ahora **compite** con los niveles 1 y 2 en lugar de ser solo fallback. Si el siguiente OnAir es posterior a `entrada + duradaOnAir`, gana el siguiente OnAir.

```javascript
// ANTES: niveles secuenciales, el 3 solo si 1 y 2 fallan
// AHORA: primario + competidor en paralelo, tomar MAX
var nextOnAirSec = this._deduceOnAirSortida(item, allLines);
if (primaryResult !== null && nextOnAirSec !== null && nextOnAirSec > primaryResult) {
    return nextOnAirSec;  // 🟡 Guanya següent OnAir (fet dur)
}
```

2. **[`calcPrecisionTrimBounds` OUT](js/core/escaleta_bounds.js:535)**: Tier 2 siempre se computa y **compite** con Tier 1. Si Tier 2 (siguiente video con OnAir) es posterior, gana con log `🟡 Tier2-COMPETE`.

```javascript
// ANTES: if (OutTier === 0) { buscar Tier 2... }  → solo si Tier 1 fallaba
// AHORA: Siempre computar tier2Candidate, y si supera a worldBlockEndSec, usarlo
if (tier2Candidate !== null && (OutTier === 0 || tier2Candidate > worldBlockEndSec)) {
    log('🟡 Tier2-COMPETE: Següent OnAir > Tier1 duradaOnAir. Guanya fet dur.');
    worldBlockEndSec = tier2Candidate;
    OutTier = 2;
}
```

3. **[`calcPrecisionTrimBounds` cap de block.out](js/core/escaleta_bounds.js:625)**: El cap de `block.out` solo se aplica cuando **no hay datos OnAir fiables** (`OutTier <= 0`). Con `OutTier > 0`, los datos de playout reales prevalecen sobre el `block.out` estructural.

```javascript
// ANTES: cap siempre aplicado
if (blockLim && blockLim.out) {

// AHORA: cap solo en fallback (sin datos OnAir)
if (blockLim && blockLim.out && OutTier <= 0) {
```

**⚠️ Nota**: Los fixes #1 y #2 funcionaban correctamente (calculaban `worldBlockEndSec=51148.00s` = 14:12:28), pero el cap de `block.out` en la línea 625 machacaba el valor a 1630.00s (14:12:10). El fix #3 corrige esto permitiendo que los datos OnAir prevalezcan.

### ✅ COMPLETADO — BUG #13: `_deduceOnAirSortida` y Tier 2 cruzan fronteras de `agrupacio`

**Archivos modificados**: [`escaleta_items.js`](js/core/escaleta_items.js), [`escaleta_bounds.js`](js/core/escaleta_bounds.js)

**Raíz del problema**: El fix del BUG #11 (competencia con siguiente OnAir) no filtraba por `agrupacio`. Tanto [`_deduceOnAirSortida`](js/core/escaleta_items.js:148) como [`calcPrecisionTrimBounds` Tier 2 Estrategia A](js/core/escaleta_bounds.js:552) competían con el siguiente `horaEntradaOnAir` de **cualquier item** en `allLines`, incluyendo ítems de otros bloques (agrupacio distinto) y totems (agrupacio null).

**Caso concreto V1 de TN_VESPRE_20260527_215506**:
- Item `222` (último IPD de V1, `agrupacio="v1"`): `horaEntradaOnAir=21:06:47`, `duradaOnAir=0:15` → sortida = 21:07:02 (76022s)
- Siguiente OnAir: item `03` (`agrupacio="v2"`) con `horaEntradaOnAir=21:08:46` (76126s)
- `_deduceOnAirSortida("222")` encontraba 76126s → `getItemSortidaSec` devolvía 76126s → OUT extendido 104s de más
- Adicionalmente, el ítem `04` (`agrupacio=null`) con `horaEntradaOnAir=21:11:04` (76264s) también contaminaba

**Fix en dos niveles**:

1. **[`_deduceOnAirSortida`](js/core/escaleta_items.js:148)**: Si el ítem tiene `agrupacio`, solo compite con ítems del **mismo** `agrupacio`. `null !== "v1"`, por tanto los totems (`null`) también se filtran. Los totems solo compiten entre ellos.

```javascript
// Línea 148
if (item.agrupacio && nextItem.agrupacio !== item.agrupacio) continue;
```

2. **[`calcPrecisionTrimBounds` Tier 2](js/core/escaleta_bounds.js:541-583)**:
   - **Estrategia A** (línea 552): mismo filtro — solo mismo `agrupacio` o sin `agrupacio`
   - **Estrategia B** (línea 563): solo para bloques **sin** `agrupacio` (`!blockAgrupacio`). Los bloques con `agrupacio` tienen fronteras definidas por Tier 1 OUT (máx entre sus items)

**Verificación de regresión para BUG #11**: El escenario del BUG #11 original (TNC V2, items sin agrupacio) no se ve afectado porque:
- Los items sin agrupacio (`null`) siguen compitiendo entre ellos (ambos tienen `agrupacio = null`, la condición `item.agrupacio && ...` es `false` → no se filtra nada)
- La Estrategia B de Tier 2 (bloques sin agrupacio) sigue activa para totems

**Commit**: pendiente
